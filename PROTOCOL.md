# Study 43: Public release cadence as a bounded review signal

## Decision, scope and acceptance

Can past stable-release intervals help identify a subsequent ninety-day release gap on other repositories and later dates? The output is a retrospective benchmark and offline dependency-review exercise. A gap means no next stable GitHub release within ninety days in the preserved current snapshot. It is not abandonment, a vulnerability, a maintenance interruption or a judgment about people. Source selection is a small authored cohort, not a representative sample or project ranking. No novelty, adoption, avoided outage or realized business saving claim.

The original proposal targeted GH Archive event histories, contributor concentration and survival models. GH Archive explicitly says its code/documentation licenses do not cover third-party rights in the event dataset. This exact study instead uses minimal factual GitHub release metadata. It does not execute contributor-concentration or developer/bot attribution analysis. Contributor identities and expressive content remain outside the public package. Descriptive inter-release survival summaries and a small fixed-horizon probability benchmark address release cadence only. This narrower outcome is explicit before cohort acquisition; preserve the original catalog proposal.

Required gates: exact source/rights/schema/pagination, immutable private originals, independent minimal-field reconstruction, fixed repository and temporal boundaries, all candidate results and failed attempts, independent prediction/denominator checks, meaningful boundary fixtures, source-preserving offline replay, three inspected figures, source-bound/rendered manuscript, scoped privacy audit, exact candidate/main CI, matching tested tree and annotated remote tag. A 4/5 means these finite conditions pass, not scientific novelty or operational reliability. Review at most three substantive rounds, forty-five active review minutes and sixty review-specific calls. Unknown gates prevent completion.

## Repository and time separation

Assign repositories by ascending SHA256 of lowercase owner/repository; alternating entries are four development and four final repositories. Persist assignment before fetching data. No project chosen or dropped from outcomes. Metadata acquisition may include the protected repositories, but no final feature, label, summary, plot or score extraction before a committed dependency freeze. Developers may see raw source envelopes while preserving them; describe this as a protected analytic evaluation, not blinded human collection.

Training origins: stable releases in development repositories published from 2020-01-01 through2022-12-31, requiring their full ninety-day label window to end by 2022-12-31T23:59:59Z. Validation: development repositories' 2023 origins with full label windows ending by 2023-12-31T23:59:59Z. Final: only final repositories' 2024-2025 origins with full label windows ending by 2025-12-31T23:59:59Z. Earlier captured releases supply history but never later feature inputs. Label y=1 when no strictly later-in-order qualifying release occurs within ninety elapsed days; a same-timestamp later release ends the gap at zero. A release exactly ninety days later counts as within the horizon. There is no observed diagnosis of maintenance failure. Preserve labels and next-release timestamps separately from predictors.

Require at least three inter-release intervals available at the origin, including the interval ending at that origin; feature is the median of those most recent three elapsed-day intervals. Do not use future release counts, current popularity, contributors, archive flags, current branch statistics, future tags or release prose. Rows without three intervals remain in the exclusion ledger, not synthetic zero-history records. At least twenty eligible origins in training, validation and final, each phase with at least one origin from each of its four assigned repositories. Otherwise report the evidence gap rather than changing the cohort or horizon. Class absence does not manufacture a positive class; report undefined recall/precision where appropriate.

## Fixed candidates and selection

Baseline p=(positive training labels+1)/(training origins+2), an authored Laplace-smoothed overall training frequency. Candidate splitpoints for recent-median cadence: 14,30,60 days. Each creates two strata <=cut and >cut. Prior strengths: 1,5,20. For each of nine settings, stratum probability=(training stratum positives + strength*baseline)/(training stratum count+strength). Empty strata return the baseline. These are small authored hypotheses, not inherited defaults, fitted causal effects or globally optimized parameters. Retain all nine settings, training counts/probabilities, runtime and validation predictions.

Select smallest validation Brier score averaged equally across the four development repositories; exact ties choose larger prior strength then smaller splitpoint. Freeze this choice, baseline, parsing/feature/metric/checker/exercise code, source/development inputs and results before any final analytic extraction. No final-driven reselection. Evaluate unchanged selected and baseline probabilities on the four other repositories and 2024-2025 origins. A later defect correction makes reused final scores retrospective. Report per-repository Brier, macro/micro Brier and log loss with an explicitly declared numerical floor 1e-12 only for log calculation, prevalence and probability-bin calibration with fixed bins [0,.2,.4,.6,.8,1]. Report confusion counts/precision/recall for authored p>=.5 review flags, with exact denominators. Flags are teaching outputs, not sent alerts or deployment policy.

Describe elapsed inter-release distributions, right-censored follow-up to each phase boundary and a descriptive Kaplan-Meier curve without treating overlapping release origins as independent people. Do not attach independent-observation confidence intervals or causal interpretations. Compare selected versus baseline finite scores and all repository failures; a baseline tie/win remains a valid result. No measured maintainer time saving, project resilience, economic cost or security risk established.
